# Limitations

Документ перечисляет известные ограничения, подводные камни и заделы проекта `securetelnet`.
Проект **учебный**: 16-битная арифметика, самодельные примитивы, отсутствие внешних
криптобиблиотек. Всё ниже — следствие этого выбора, а не список багов, которые нужно
немедленно исправить. Для каждого пункта указано, что именно ограничено и как это
обойти, если понадобится.

## 1. Криптостойкость

### 1.1. DH на 16 битах

`S = G^(a·b) mod P`, `P = 65519`, `P-1 = 65518 = 2·7·31·151`.

- Пространство секретов `a, b ∈ [1, P-2] ≈ 2^16`.
- BSGS: ~256 шагов и ~256 памяти → **миллисекунды** на современном CPU.
- Перебор `a` по `A = G^a mod P` — тривиален.
- **Следствие:** любой пассивный наблюдатель восстанавливает `S` из handshake.
- **Обход:** заменить на Curve25519 (32-байтные ключи, 32-битная арифметика) или
  DH на `P ≥ 2^2048` (не влезает в AVR, влезает в x86).

### 1.2. `ks16` — не криптостойкая OWF

`ks16(S, ctr) = (((S^ctr) | 1) mod P)^3 mod P`.

- `x^3 mod P` **обратим** при известном `D_INV = 3^(-1) mod (P-1) = 43679`.
- `D_INV` публичен (константа в `algo.h`), `P-1` факторизуется за миллисекунды.
- **Следствие:** `ks16` — биекция, а не OWF; при известном plaintext-ciphertext
  пара даёт keystream, из которого перебором 65536 значений `S` восстанавливается `S`.
- **Обход:** ChaCha20 / SipHash-2-4 / SHA-256 (внешние библиотеки).

### 1.3. MAC не покрывает данные

`tag = ks16(S, ctr ^ 0xFFFF)` — 2 байта, зависит только от `S` и `ctr`.

- **Защищает от:** replay (другой `ctr` → другой `tag`), перестановки пакетов, потери.
- **Не защищает от:** подмены ciphertext внутри сессии. Пакет можно заменить,
  сохранив `ctr` и `tag`; получатель расшифрует мусор, `tag` сойдётся.
- **Следствие:** целостность payload не гарантируется.
- **Обход:** `tag = HMAC(hash(S), ctr || ciphertext)` или AEAD (ChaCha20-Poly1305).

### 1.4. PRNG `xorshift32`

- Не криптостойкий: состояние — 32 бита, предсказуемо при известном seed.
- Seed: `time(NULL) ^ (getpid() << 16) ^ clock()` — предсказуем.
- **Следствие:** `r` в Schnorr и nonce в DH предсказуемы; повторное использование `r`
  при разных `c` раскрывает `priv` (`(s1-s2)/(c1-c2) = priv`).
- **Обход:** `getrandom()` / `/dev/urandom` для seed и для `r`.

### 1.5. Нет аутентификации сервера

- Клиент проверяет только серверный `B` на диапазон, но не подпись.
- **Следствие:** MITM подменяет `B`, встаёт посередине; Schnorr клиента бесполезен
  против такого MITM (он ретранслирует proof).
- **Задел:** `load_pub` в `server.c` уже есть, но не вызывается.
- **Обход:** сервер подписывает `S` (или `B || nonce_s`) своим `priv_server`,
  клиент проверяет через `schnorr_verify_cfg(pub_server, ...)`.

### 1.6. Нет forward secrecy

- `S` фиксирован на сессию; при компрометации `priv` или переборе `a` раскрывается `S`
  для **всех** прошлых сессий, если записан трафик.
- **Обход:** re-keying после N пакетов/секунд (новый DH поверх текущего канала,
  старый `S` затирается).

### 1.7. `c = 0` в Schnorr

- `c = ks16_cfg(S, rnd) ^ 0xFFFF` может дать `0` с вероятностью `1/65536`.
- При `c = 0`: `s = r`, `G^s = R` — проверка проходит **без знания `priv`**.
- **Текущее состояние:** `c` принудительно заменяется на `1` в `auth_schnorr_server`.
- **Обход:** уже сделан; для строгости — генерировать `c` в `[1, P-2]` напрямую.

### 1.8. `R = 0` в Schnorr

- `R = 0` невозможен при `r ∈ [1, P-2]` (так как `G^r ≠ 0 mod P` для простого `P`),
  но если бы был — `rhs = 0`, `lhs = G^s ≠ 0` → verify провалится.
- **Текущее состояние:** сервер отвергает `R = 0` явно (`if (R == 0)`).

### 1.9. Коллизии `ks16`

- `(c, c^1)` при чётном `(S^c)` дают одинаковый `x` после `|1`, значит одинаковый `ks16`.
- Вероятность `~1/32768` на случайную пару `(S, c)`.
- **Следствие:** keystream может повториться на двух соседних `ctr`.
- **Текущее состояние:** не лечится; в `test_algo` печатается оценка `observed/expected`
  без `FAIL`.
- **Обход:** убрать `| 1` и заменить на `x = (x == 0) ? 1 : x;` — коллизии останутся
  для `(c, c^1)` при `x = 1`, но исчезнут для остальных.

### 1.10. MAC коллизия `tag(0) = tag(0xFFFF)`

- `tag = ks16(S, ctr ^ 0xFFFF)`; `ctr = 0` и `ctr = 0xFFFF` дают одинаковый `tag`.
- **Следствие:** при переполнении `uint16_t` счётчика (65 536 пакетов) возможна
  коллизия тега.
- **Текущее состояние:** за сессию 65 536 пакетов маловероятно, но возможно при
  длинной сессии.
- **Обход:** при `ctr == 0xFFFF` — сброс сессии (новый DH) или переход на `uint32_t ctr`.

## 2. Протокол

### 2.1. Negotiation — строгое равенство

- `choose(client, server)` возвращает `client` только если `client == server`, иначе `-1`.
- **Следствие:** клиент с `--kdf byte` и сервер с `--kdf cube` не договорятся.
- **Обход:** negotiation по диапазонам предпочтений (клиент шлёт список, сервер выбирает
  первый общий).

### 2.2. `version = 0` как отказ

- Сервер при несовместимости шлёт 9 нулевых байт (`version = 0`).
- Клиент трактует `version != PROTO_VERSION` как `negotiate failed`.
- **Ограничение:** нет расширяемого списка причин отказа.

### 2.3. `ctr_tx` и `ctr_rx` независимы

- Оба стартуют с `peer_nonce` (low 16 bits), дальше инкрементируются независимо.
- **Следствие:** порядок пакетов в каждом направлении сохраняется TCP; при потере
  пакета (что TCP не допускает) счётчик разойдётся.
- **Ограничение:** нет окна переупорядочивания, нет обработки вне-порядковых пакетов
  (не нужно для TCP, но нужно для UDP-транспорта).

### 2.4. `MAX_PAYLOAD = 65535`

- `uint16_t len` в `send_packet`/`recv_packet`.
- **Следствие:** один пакет ≤ 64 КБ; файлы > 64 КБ отвергаются в `mode_file`
  (`uint16_t flen`).
- **Обход:** 4-байтовый `flen` + блоки по 1024/4096 (см. `docs/PROTOCOL.md`,
  раздел «File transfer extensions»).

### 2.5. Keepalive и таймаут

- `keepalive_interval = 30 с`, `keepalive_timeout = 90 с` — константы в `session_open`.
- **Следствие:** при долгом простое обе стороны шлют пустые пакеты; при обрыве
  сессия закрывается через 90 с.
- **Ограничение:** не настраивается через CLI (только правкой кода).

### 2.6. `session_open` и коллизии имён

- Путь: `<dir>/session_YYYYMMDD_HHMMSS.log`.
- **Следствие:** два параллельных запуска в одну секунду с одинаковым `dir` дадут
  один файл (второй `fopen("w")` затрёт первый).
- **Обход:** добавить `pid` или счётчик в имя.

## 3. File mode

### 3.1. `flen` — 2 байта

- Файлы > 65535 байт отвергаются (`file too large`).
- **Обход:** 4-байтовый `flen` + блоки (см. `docs/PROTOCOL.md`).

### 3.2. `path_is_safe` отвергает `..` даже после нормализации

- `path_is_safe("sub/../x")` → `0` (из-за `..`), хотя после нормализации путь безопасен.
- **Следствие:** нельзя использовать относительные пути с `..` для выхода и возврата
  в подкаталог.
- **Обход:** нормализовать путь (`realpath`) перед проверкой, или явно разрешить
  `..` внутри `cwd`.

### 3.3. `--no-overwrite` + автотесты

- При `--no-overwrite` сервер пишет в `remote.1`, `remote.2`, ... если `remote` занят.
- **Следствие:** автотест, который ожидает `remote`, не найдёт файл.
- **Текущее состояние:** `tests/run_file_tests.sh` использует `--overwrite` по умолчанию.

### 3.4. `put` и `get` используют один и тот же `<path>` на обеих сторонах

- `put <local> <remote>` и `get <remote> <local>` — с двумя путями (после патча).
- **Ограничение:** нет способа передать файл «во временный каталог» без явного пути.
- **Обход:** указать полный относительный путь в `--file-cmd`.

### 3.5. `get` не отвечает серверу

- После получения файла клиент завершается, сервер ждёт `recv_packet` → EOF → `break`.
- **Следствие:** нет явного `ACK` от клиента; сервер не знает, что клиент сохранил файл.
- **Ограничение:** при обрыве клиента сервер не отличит «сохранил» от «упал».
- **Обход:** добавить финальный `ACK` от клиента (1 байт) и ждать его на сервере.

## 4. Shell mode

### 4.1. Нет `termios` raw

- `Ctrl-C` убивает клиента локально, а не удалённый shell.
- Стрелки/`Ctrl-D` работают как в обычном терминале (буферизация строки).
- **Следствие:** shell-режим неудобен для интерактивной работы.
- **Обход:** `termios` raw на клиенте + передача `SIGINT` как байта `0x03`
  в поток; на сервере — `write` в `socketpair` ребёнка.

### 4.2. `fork`/`execvp` — только Linux/POSIX

- На Windows shell-режим не работает без `_spawn`/`CreateProcess`.
- **Ограничение:** проект ориентирован на Linux.

### 4.3. Нет ограничения ресурсов shell

- `execvp(shell)` без `setrlimit`/`chroot`/`setuid`.
- **Следствие:** shell имеет те же права, что и сервер.
- **Обход:** `setuid`/`setgid`/`chroot` перед `execvp` (требует root).

## 5. Chat mode

### 5.1. Нет `readline`

- `fgets` + `select` + `\r`-перерисовка.
- **Следствие:** набранный, но не отправленный текст теряется при входящем сообщении.
- **Обход:** GNU `readline` или raw-mode + собственная строка ввода.

### 5.2. Нет истории, редактирования, автодополнения

- Ограничение `fgets`: нет стрелок, `Ctrl-A`, `Ctrl-E` и т.д.

### 5.3. Приглашение ломается при входящем сообщении без `\r`

- В `mode_chat` используется `printf("\r<peer>> %s\n<self>> ", ...)`.
- **Следствие:** если убрать `\r`, приглашение «съезжает» на новую строку.
- **Текущее состояние:** `\r` включён.

## 6. Ресурсы

### 6.1. `MAX_PAYLOAD = 65535` на стеке

- `mode_file` держит `uint8_t in[MAX_PAYLOAD]` на стеке — 64 КБ.
- `send_packet` держит `uint8_t cbuf[COMPRESS_BUF]` — 128 КБ на стеке.
- **Следствие:** на x86-64 нормально (стек 8 МБ), на AVR/ESP32 — переполнение стека.
- **Обход:** `static` буферы или уменьшить `COMPRESS_BUF`/`MAX_PAYLOAD` до 512/4096.

### 6.2. `g_cbuf[COMPRESS_BUF]` — глобальный буфер 128 КБ

- В `proto.c` — глобальный, не на стеке.
- **Следствие:** на MCU с 64 КБ RAM не поместится.
- **Обход:** уменьшить `COMPRESS_BUF` или сделать динамическим.

### 6.3. `g_cache_arr[256]` — 512 байт

- Кэш `pub^c` в `schnorr_verify_cfg` при `schnorr_cache = 1`.
- **Следствие:** 512 байт глобально; на AVR ощутимо.
- **Обход:** не включать `--schnorr cache` на слабых MCU.

## 7. Тесты и бенчмарки

### 7.1. `test_algo` использует `clock()` для seed

- Seed: `time ^ (pid << 16) ^ clock()`.
- **Следствие:** при быстром повторном запуске seed может совпасть.
- **Обход:** `getrandom()` для seed.

### 7.2. `bench` измеряет только CPU

- `stream_xor`, `ks16`, `modpow` — без TCP, `read`/`write`, `select`.
- **Следствие:** `Mbps` в `bench` — верхняя граница; реальная пропускная способность
  ниже из-за syscall/TCP overhead.
- **Обход:** измерять `run_file_tests.sh` с `time` для end-to-end throughput.

### 7.3. `run_file_tests.sh` — `sleep 0.3`

- Ждёт, пока сервер `bind`/`listen`.
- **Следствие:** на медленной машине сервер может не успеть — клиент получит
  `connect: Connection refused`.
- **Обход:** цикл ожидания `nc -z 127.0.0.1 $PORT` вместо `sleep`.

### 7.4. `run_file_tests.sh` — полная матрица

- 3 kdf × 3 cipher × 3 compress × 2 auth × 3 prng × 2 mac × 2 schnorr × 2 dh = 1296
  комбинаций на файл × 8 файлов ≈ 10 368 запусков.
- **Следствие:** полный прогон — часы.
- **Обход:** OFAT-матрица (one-factor-at-a-time): baseline + по одному отклонению
  на опцию = 13 запусков на файл.

## 8. CLI и UX

### 8.1. Нет `--version`

- Версия `PROTO_VERSION = 1` только в `proto.h`.
- **Обход:** `grep PROTO_VERSION include/proto.h`.

### 8.2. Нет `--help` с кодами возврата

- `usage()` печатает синтаксис, но не объясняет значения `--kdf`/`--cipher`/...
- **Обход:** читать `docs/API.md`.

### 8.3. Нет конфиг-файла

- Все параметры — через CLI.
- **Следствие:** длинные команды; нет сохранения настроек.
- **Обход:** shell-скрипт или `Makefile`-цель.

### 8.4. `--dh test` не запрещён в продакшене

- `DH_TEST` ограничивает `a, b ∈ [1, 256]` — снижает стойкость DH ещё сильнее.
- **Следствие:** случайное использование `--dh test` ломает безопасность.
- **Обход:** сервер отвергает `dh_mode == DH_TEST`, если не задан `--allow-test`.

## 9. Безопасность процессов

### 9.1. `authorized_keys` читается при старте

- Отзыв ключа — только рестарт сервера.
- **Обход:** перечитывать по `SIGHUP` или при каждом `accept`.

### 9.2. Логи содержат `S` и ключи

- `session_log(sess, "dh ok S=%04x", *S)` и `auth OK S=%04x`.
- **Следствие:** компрометация логов раскрывает `S` (и через `S` — keystream).
- **Обход:** не логировать `S`, логировать только `hash(S)`.

### 9.3. Нет rate-limiting

- `accept` → сразу handshake; нет защиты от флуда.
- **Следствие:** DoS через множество подключений.
- **Обход:** `SO_REUSEADDR` + счётчик одновременных сессий + `sleep` при ошибке.

### 9.4. Нет таймаута на handshake

- `dh_client_cfg`/`dh_server_cfg` блокируются на `read_full`.
- **Следствие:** медленный клиент держит сервер.
- **Обход:** `select` с таймаутом перед `read_full`, или `SO_RCVTIMEO`.

## 10. Совместимость

### 10.1. Только Linux/POSIX

- `fork`, `execvp`, `socketpair`, `select`, `termios` (не используется) — POSIX.
- **Следствие:** на Windows нужен WSL или порт на `CreateProcess`/`WSAPoll`.

### 10.2. `liblz4` опциональна

- Без `liblz4-dev` `lz4_compress_wrap` возвращает `-1`.
- **Следствие:** negotiation с `--compress lz4` не пройдёт, если хотя бы одна сторона
  собрана без `HAVE_LZ4`.
- **Обход:** `sudo apt install liblz4-dev`; или использовать только `rle`.

### 10.3. 16-битная арифметика

- `uint16_t` для `S`, `priv`, `pub`, `ctr`, `len`.
- **Следствие:** на 8-бит AVR (Uno/Nano) `uint32_t` умножение — программное, `modpow`
  ~2 мс; на ESP32 — быстрее.
- **Ограничение:** `MAX_PAYLOAD=65535` и 128 КБ `COMPRESS_BUF` не влезают в AVR.

## 11. Заделы на будущее (не реализовано)

| Функция | Сложность | Что даёт |
|---|---|---|
| Аутентификация сервера | средняя (~40 строк) | закрывает MITM |
| Re-keying | средняя (~50 строк) | forward secrecy |
| 4-байтовый `flen` + блоки | низкая (~10 строк) | файлы до 4 ГБ |
| `termios` raw + `SIGINT` | средняя (~80 строк) | нормальный shell |
| MAC по `hash(S, ctr, ct)` | низкая | детект подмены payload |
| Negotiation по диапазонам | средняя | гибкость |
| Порт-форвардинг | высокая (~150 строк) | как `ssh -L` |
| `SIGHUP` для `authorized_keys` | низкая | отзыв ключей без рестарта |
| `getrandom()` для seed | низкая | криптостойкий PRNG |
| `--version` | тривиальная | UX |

## 12. Сводка: что можно и что нельзя

**Можно:**
- Изучать структуру DH + Schnorr + negotiation + потокового шифра на целочисленной
  арифметике.
- Сравнивать варианты `kdf`/`cipher`/`mac`/`prng`/`compress` в `bench` и `test_proto`.
- Передавать файлы ≤ 65535 байт между двумя Linux-машинами.
- Использовать как основу для учебного проекта по сетевой безопасности.

**Нельзя:**
- Защищать реальные секреты.
- Использовать в продакшене.
- Полагаться на MAC как на защиту целостности payload.
- Считать `S` секретом при записи трафика (16-бит DH ломается).
- Запускать на AVR/ESP32 без уменьшения `MAX_PAYLOAD`/`COMPRESS_BUF`.
